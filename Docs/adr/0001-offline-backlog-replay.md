# 离线积压 + 服务端按模块重放的合成存档同步

合成存档需要离线可玩，同时由服务端裁决。我们选择：客户端先执行操作，并按顺序累积为积压；服务端用与客户端同一份确定性规则代码按序重放校验，版本按模块划分。不选每步都等服务端确认，因为那样无法离线；不选客户端权威上传快照，因为那样无法防作弊；不选整份存档一个版本号，因为那样一台设备的任何改动都会让另一台设备的全部离线进度作废。

## Consequences

- 模块：每块棋盘（含其订单）、共用资源（体力、货币）、邮件领取状态各是一个模块，各有版本号。每条被接受的操作会让它碰到的所有模块的版本号加 1。
- 每条操作携带它碰到的全部模块的版本号，全部一致才执行。大多数操作都会碰到共用资源，所以多设备冲突时，按模块分版本能挽救的主要是不碰共用资源的操作。
- 一条操作被拒绝后，它碰到的所有模块标记为失效；积压里后续操作只要碰到失效模块就一律拒绝，只碰健康模块的操作继续执行。失效模块由服务端整块下发，覆盖客户端本地。
- 同步以模块为单位整块替换，不使用 proto 字段级 Merge，因为 proto 合并时列表会追加，零值和空值也表达不出来。存档结构演进按 proto 兼容规则（新字段用新编号，旧编号不复用），老存档不写迁移。
- 随机数不是模块：存档里有一个创建后不再改变的基座种子，各模块需要随机时，用"基座种子 + 模块标识 + 模块内随机计数"确定性地算出结果。计数只在真正消耗随机时才加 1，所以移动这类不碰随机的操作没法用来"重刷"结果；双端算法一致，重放结果就一致。
- 每条操作携带客户端时间；服务端把它限制在“不早于上一条操作、不晚于服务端收到积压的时刻”的范围内，改时钟最多只能把进度预支到当前时刻。
- 存档记录配置版本，积压的配置版本与服务端当前版本不一致时，整批拒绝。
- 服务端从不直接改存档：发奖只走邮件，领取邮件是一种只能在线发起的操作；开启棋盘也是一种操作。
- 只有至少在线登录过一次才能离线启动；积压实时落盘，设有条数上限，超过上限必须联网。
